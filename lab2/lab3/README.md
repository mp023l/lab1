# Задание 3 — Аукцион коллекционных предметов, вариант 18

Java 21, Spring Boot 3.4.4, Spring JDBC, **реляционная БД H2 с хранением в файле**. Продолжение REST-проекта из задания 2. Сервис проводит аукционы коллекционных предметов: от создания лота до определения победителя и передачи предмета.

## Запуск — без установки БД

1. Распакуйте архив целиком.
2. Дважды нажмите **ЗАПУСТИТЬ.cmd**. Java 21 автоматически находится в JAVA_HOME, папке JDK IntelliJ или PATH.
3. Дождитесь строки `Started AuctionApplication`. Откройте http://localhost:8080/api/users.

Окно оставьте открытым; остановка — Ctrl+C. Для повторного запуска нажмите тот же файл. Готовый `app.jar` уже включён в архив. Если порт 8080 занят другим запуском проекта, сначала закройте старое окно.

База создаётся автоматически в `data/auction.mv.db`; данные **сохраняются после перезапуска**. Пароли администратора и ограниченного пользователя генерируются при первом запуске в `.env`. Не удаляйте `.env` отдельно от базы: он нужен для повторного подключения. Эти файлы исключены из Git и не входят в исходный архив.

Для IntelliJ IDEA: откройте `pom.xml`, выберите JDK 21, рабочую папку проекта и запустите `AuctionApplication`. Настройки БД менять не нужно. Не запускайте одновременно второй экземпляр приложения.

## Предметная модель

| Сущность | Назначение и связи |
|---|---|
| Пользователь | Имя, уникальный email; владеет предметами и делает ставки. |
| Предмет | Описание, состояние, текущий владелец → пользователь. |
| Лот | Предмет, начальная цена, шаг, время, статус. У предмета много лотов в истории, один зарезервированный одновременно. |
| Ставка | Лот, участник, сумма, время сервера. У лота много ставок. |
| Сделка | Лот, победившая ставка, сумма, статус передачи. Не больше одной сделки на лот. |

В БД настроены PK, FK, NOT NULL, UNIQUE, CHECK и запрет удаления связанных записей. Суммы положительные, NUMERIC(14,2); конец аукциона позже начала. Составной FK сделки гарантирует принадлежность победившей ставки этому лоту и совпадение суммы. Уникальный индекс по вычисляемому полю запрещает несколько OPEN/CLOSED лотов для одного предмета.

## Пять бизнес-операций

Все адреса используют POST:

| Операция | Адрес | Правила и результат |
|---|---|---|
| Публикация | `/api/auction-lots/{id}/publish` | Только DRAFT с ещё не истёкшим сроком; предмет свободен. Лот → OPEN. |
| Ставка | `/api/auction-lots/{id}/place-bid` | JSON `{"userId":2,"amount":1100}`. Только OPEN в пределах времени торгов; владелец не участвует. Первая сумма ≥ начальной, следующая ≥ максимальной + шаг. |
| Закрытие | `/api/auction-lots/{id}/close` | Только после окончания OPEN. Максимальная ставка создаёт PENDING-сделку и CLOSED-лот. Без ставок — UNSOLD, без сделки. |
| Отмена | `/api/auction-lots/{id}/cancel` | Только DRAFT/OPEN без ставок → CANCELLED. |
| Завершение сделки | `/api/auction-deals/{id}/complete` | Только PENDING и CLOSED: предмет переходит победителю, сделка → COMPLETED, лот → SETTLED. Повтор запрещён. |

Ставка, закрытие и завершение используют несколько сущностей и зависят от их состояния. Все изменения выполняются в транзакциях с блокировкой служебной строки `SELECT ... FOR UPDATE`. Параллельные ставки согласованы; при ошибке откатывается вся операция. Внешняя оплата не моделируется: завершение фиксирует передачу предмета в учебной предметной области.

## REST API и демонстрация

Ресурсы задания 2 сохранены: `/api/users`, `/api/collectible-items`, `/api/auction-lots`, `/api/bids`, `/api/auction-deals`. Для каждого предусмотрены GET списка, GET `/{id}`, POST, PATCH/PUT `/{id}`, DELETE `/{id}`. PUT требует полное тело, PATCH — изменяемые поля.

Редактировать и удалять можно только черновики лотов; связанных пользователей и предметы удалять нельзя. Владельца предмета меняет только завершение сделки. PATCH/PUT/DELETE ставок и сделок возвращают 409: историю торгов нельзя подменять или стирать. `POST /bids` применяет правила ставки; `POST /auction-deals` закрывает истёкший OPEN-лот, проверяя победителя и сумму. Прямое изменение статусов в обход бизнес-операций запрещено.

Коды: 201 + Location — создание; 200 — чтение/изменение; 204 — удаление; 400 — неверные данные; 404 — отсутствие; 409 — конфликт состояния или ограничений.

Импортируйте `postman/Auction.postman_collection.json` в Postman → **Run**, все **53 запроса**, 1 iteration. Таймаут scripts ≥ 60000 мс. Коллекция сама готовит уникальные данные, сохраняет ID, выполняет все операции, проверяет ошибки и нового владельца. Один запрос ждёт окончания 20-секундного аукциона. Повторные прогоны поддерживаются. Для ручной проверки из IDEA есть `requests.http`.

## Реализация и проверка

`AuctionController` — CRUD; `OperationsController` — бизнес-команды; `AuctionService` — правила/транзакции; `AuctionRepository` — параметризованный SQL; `Resource` — белый список полей; `LocalDatabaseConfiguration` — файловая БД, демоданные и ограниченный пользователь. SQL находится в `src/main/resources/db/`.

Приложение работает от `auction_app`, без прав администратора и создания таблиц. На ставки разрешены только SELECT/INSERT, на сделки — SELECT/INSERT/UPDATE. Администратор используется лишь при первоначальной подготовке БД и выдаче прав. Тестовые записи автоматически создаются для всех пяти сущностей один раз.

`mvn test` — проверки бизнес-сценариев, параллельных ставок, отката и HTTP, а также реального сохранения файловой БД и ограничений роли. Сборка: `mvn package`. Для сдачи исходники, SQL, README и Postman уже находятся в этом архиве.
