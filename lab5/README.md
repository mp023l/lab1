# Лабораторная работа №5 — JWT Access/Refresh, ротация сессий

Основа: `lab4` из пользовательского репозитория. Предыдущие API, роли и проверки `@PreAuthorize` сохранены. Новая аутентификация: **Bearer JWT**, вместо Basic и cookie/CSRF из четвёртой лабораторной.

## Запуск

Требуется Java 21, Maven и переменные окружения `JWT_SECRET` и `AUCTION_ADMIN_PASSWORD` (при первом запуске базы).

PowerShell 5.1, генерация секрета (один раз):

```powershell
$bytes = New-Object byte[] 32
[System.Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($bytes)
$env:JWT_SECRET = [Convert]::ToBase64String($bytes)
$env:AUCTION_ADMIN_PASSWORD = 'ReplaceWithYourOwnStrong12!'
mvn spring-boot:run
```

**Важно:** не публикуйте настоящий секрет или пароль. При последующих запусках с той же БД сохраняйте тот же `JWT_SECRET`, иначе старые токены перестанут проверяться. Не храните секрет в Git.

`POST /auth/register` (201), `POST /auth/login` (200), `POST /auth/refresh` (200) возвращают `accessToken` и `refreshToken`. При входе используется `username` (как в lab4), а не email. Access живёт 15 минут, refresh — 7 дней. Токены подписываются HS256, имеют уникальные `jti`, `sid` и обязательный `type`.

## Хранение и ротация

В таблице `user_sessions` хранятся идентификатор сессии, аккаунт, `device_id`, идентификаторы токенов, SHA-256 хэш refresh, сроки и статус. Сами refresh-токены в базе не сохраняются.

Ротация проводится в транзакции с `SELECT ... FOR UPDATE`. Исходная запись переходит из `ACTIVE` в `USED`, новая пара записывается в `ACTIVE`. Повторное предъявление использованного refresh возвращает 401 и **фиксирует** переход `USED` → `REVOKED` (без отката транзакции). `REVOKED` и истёкшие сессии не обновляются. Отзыв refresh не отменяет уже выпущенный access до его истечения.

Access принимается только в `Authorization: Bearer <token>`. Refresh никогда не принимается для доступа к API. Права пользователя загружаются из БД на каждом запросе, чтобы изменения роли и блокировка применялись сразу.

## Проверка

Запустите примеры `requests.http` и `mvn test`. Успешные сценарии: регистрация, вход, доступ, однократное обновление. Негативные: неправильный пароль, отсутствие токена, поддельный токен, refresh вместо access, повторное использование refresh, недостаточные права. Проверить таблицу `user_sessions` можно в H2.
